# Потоковый ответ и озвучка

Состояние на 17.11.2026, ветка `feature/dialog-mode`.

## Зачем

Раньше ход диалога ждал весь ответ модели, потом целиком отдавал его в
TTS, и только тогда начинал звучать первый фрагмент. На длинном ответе
это давало несколько секунд тишины после вопроса.

Теперь модель отдаёт текст кусками (SSE), а озвучка режет его на
фрагменты и синтезирует их параллельно: первая фраза звучит, пока
догенерируется остальное.

## Как устроено

- `CloudLLM.chat_stream()` — тот же OpenAI-совместимый запрос, но
  `stream: true`; читает `data:`-строки и отдаёт только `delta.content`.
  Служебные строки, битый JSON и пустые дельты пропускаются.
- Запасная модель включается, только пока не пришёл первый кусок. После
  начала ответа переключение запрещено: пользователь услышал бы два
  разных начала. Обрыв после первого куска заканчивает ответ, уже
  сказанное остаётся.
- `DialogService.reply(text, on_chunk=...)` включает поток, если
  `dialog.streaming.enabled`, передан колбэк и у модели есть
  `chat_stream`. Иначе работает прежний путь одним запросом. В историю
  попадает полный текст после завершения; частичный ответ при обрыве
  тоже сохраняется, чтобы следующий ход видел, что было сказано.
- `TTSService.stream()` создаёт задачу с пустой очередью; `feed()`
  добавляет текст, `close()` закрывает задачу и отправляет остаток.
  Воркер сам добирает фрагменты из очереди, поэтому синтез и
  проигрывание идут одновременно с генерацией ответа.
- Очередь одна: поток `tts-worker` играет фрагменты строго по одному.
  Пока звучит текущий, отдельный поток `tts-submit` сразу отдаёт в пул
  `tts.workers` новые фрагменты, которые приносит `feed()`. Впереди
  держится не больше `workers + 1` фрагментов: очередь не отправляет в
  API весь ответ сразу, чтобы отмена не оплачивала текст, который уже
  не прозвучит.
- Раньше отправкой занимался сам проигрыватель между фрагментами, и
  текст, пришедший во время звука, ждал конца фразы. На стыке первого и
  второго предложения это давало паузу в 1–2.5 с: второй фрагмент
  начинал синтезироваться только после того, как отзвучал первый.
  Теперь синтез идёт параллельно с воспроизведением.
- Фрагменты режутся по `.`, `?`, `!` и `…`. Запятая, двоеточие, точка
  с запятой и тире используются только для предложений длиннее
  `STREAM_CHUNK_LIMIT` (180 символов), которые не помещаются в лимит.
  Короткая фраза с запятой уходит в TTS целиком: это важнее, чем
  сэкономить несколько десятых секунды на старте.
- Ошибка синтеза одного фрагмента не рвёт очередь: фрагмент
  пропускается, следующий играет. Три ошибки синтеза подряд
  останавливают остаток ответа, чтобы не ждать таймауты на каждом куске.
- Ошибка воспроизведения тоже пропускает фрагмент; две подряд
  останавливают остаток, чтобы не долбить мёртвое аудиоустройство.
- `tts.chunk_wait_sec` ограничивает ожидание синтеза, когда предыдущий
  фрагмент уже доиграл. Не готов — фрагмент пропускается, очередь идёт
  дальше. `0` отключает предел.
- `tts.prebuffer_sec` — необязательный буфер перед стартом фрагмента:
  подождать следующий, если он уже синтезируется. По умолчанию `0`:
  задерживать первый звук ради страховки нет смысла, паузы лечит
  параллельная отправка.
- Каждый фрагмент пишет в лог строку `TTS: фрагмент N/M, K симв.,
  синтез A с, ждал B с, буфер C с, пауза D с, звук E с`. По ней видно,
  где именно теряется время.
- `stop()` по-прежнему отменяет задачу: новые `feed()` после отмены
  игнорируются, а `dialog.reply` дочитывает поток молча.
- Вызовы PortAudio остаются в потоке-воркере TTS. Новых обращений к
  `sounddevice` из чужих потоков нет.

## Интонация

Каждый фрагмент — отдельный запрос к `/v1/audio/speech`, поэтому TTS не
знает, что было в предыдущем. Голос и громкость фиксированы (`voice`,
нормализация к −20 dBFS), но просодия на стыках может отличаться.

В документации ProxyAPI у эндпоинта перечислены только `input`, `voice`,
`response_format`, `speed` и `instructions`; `previous_text` / `next_text`
там нет. Поле `previous_text` API принимает (HTTP 200), но доказать, что
оно влияет на синтез, нельзя: ответы стохастичны, контрольные запросы
тоже отличаются. Поэтому контекст предыдущего фрагмента не передаём и
не делаем вид, что он работает.

Что делаем вместо этого: не режем короткие фразы по запятым, отдаём TTS
целые предложения и держим одинаковый голос и громкость. Это убирает
самый заметный источник рваной интонации — фрагмент, оборванный на
середине придаточного.

## Настройки

```json
"dialog": {
  "streaming": {
    "enabled": true
  }
},
"tts": {
  "workers": 3,
  "chunk_wait_sec": 30,
  "prebuffer_sec": 0
}
```

Включать поток есть смысл только вместе с озвучкой: без TTS поток не
даёт выигрыша, а ответ всё равно произносится в конце (если TTS доступен).

## Замеры

Живая проверка через ProxyAPI, модель `anthropic/claude-haiku-5-5`,
ответ ~600 символов, старая схема с обрывом первого фрагмента по запятой:

- первый кусок модели — 0.9–1.2 с, весь ответ — 2.2–2.4 с;
- первый звук — 2.2–3.5 с (до изменений ждали весь ответ плюс синтез
  первого предложения, на этом ответе — около 13 с);
- синтез фрагмента занимает примерно 0.6–0.9 от длительности звука, но
  разброс у провайдера большой: фрагмент на 8 секунд звука иногда
  синтезируется 3 с, иногда 13 с. Поэтому паузы между фрагментами
  возможны, особенно на первом длинном предложении.

После отказа от обрыва по запятой первый фрагмент стал длиннее на одно
предложение. На короткой первой фразе разницы почти нет; на длинном
первом предложении старт может сдвинуться на 0.5–2 с. Это осознанный
размен: естественная интонация важнее мгновенного старта.

Живая проверка новой схемы (три предложения, синтез настоящий, звук не
выводился): первый звук — 2.0 с, пауз между фрагментами не было.

Отдельный замер паузы на стыке, три предложения с задержкой подачи 0.6 с
(как в потоке модели), синтез настоящий:

- до исправления: второй фрагмент ждал 2.1–2.8 с, слышимая пауза —
  2.1–2.8 с;
- после: `ждал 0.00 с, пауза 0.00 с` на обоих стыках, общее время
  ответа 14.5 с;
- с `prebuffer_sec=0.8`: паузы тоже нет, но первый звук сдвигается на
  0.8 с. Поэтому буфер по умолчанию выключен.

Синтез у провайдера идёт примерно 0.35–0.6 от длительности звука на
коротких фразах (2.0 с синтеза на 2.9 с звука), но разброс большой:
раньше на длинном предложении встречалось 6 с синтеза на 4.5 с звука.
Параллельная отправка убирает паузу, пока синтез следующего фрагмента
укладывается в звучание текущего; если провайдер станет медленнее речи,
паузы вернутся — тогда и стоит включать `prebuffer_sec`.

Кэш TTS (`tts.cache_dir`) работает как раньше: повторные фразы звучат
мгновенно.

## Ограничения

- **Просодия между фрагментами.** Каждый фрагмент синтезируется
  независимо; тембр и громкость выровнены, но интонация на стыках может
  отличаться. Настоящий stitching требует провайдера с контекстом
  предыдущего текста; в текущем эндпоинте его нет.
- **Перебить во время генерации нельзя.** Главный цикл занят чтением
  потока, как раньше был занят ожиданием ответа. Стоп-слово и wake word
  работают во время проигрывания, когда управление уже вернулось в цикл.
  Чтобы перебивать в любой момент, генерацию надо уводить из главного
  цикла отдельным потоком — следующий шаг, не в этом изменении.
- **Эхо.** Микрофон слышит собственный ответ из колонок. Пока
  пользуемся наушниками; эхо-подавление не делалось.
- **История после перебивания.** Если пользователь перебил озвучку,
  модель всё равно догенерирует ответ, и в историю попадёт полный текст,
  включая то, что не прозвучало. Следующий ход будет считать, что это
  было сказано.

## Проверка

- Полный прогон: 1049 тестов, ruff чистый.
- Тесты нарезки: короткая фраза с запятой не режется; длинное
  предложение режется по запятой; без запятой — по словам.
- Тесты очереди: следующий фрагмент синтезируется, пока текущий ещё
  играет; текст, пришедший во время звука, уходит в синтез сразу, не
  дожидаясь конца фразы; ошибка синтеза и ошибка воспроизведения
  пропускают один фрагмент, а не весь ответ.
- Живой SSE через ProxyAPI: поток идёт, первый кусок раньше полного
  ответа, запасная модель не включается без нужды.
- Сквозная проверка с живым синтезом (звук не выводился): первый
  фрагмент зазвучал через 2.0 с, очередь дошла до конца, ни один
  фрагмент не потерялся, пауз между фрагментами нет.
